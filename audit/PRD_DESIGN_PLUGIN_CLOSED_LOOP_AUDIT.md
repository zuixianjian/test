# PRD、设计图与插件数据闭环审查

审查日期：2026-11-13。被审查版本：1.0.15。

**结论：目前只有部分流程形成了闭环，不能按“所有页面数据可信、所有按钮上下游完善、所有模块已闭环”验收。**

本次只新增审查脚本、清单和证据，不修改业务代码或重新发布插件。原有 33 项回归覆盖的是特定正向路径；它们通过不等于 PRD 全量符合。本轮扩展场景复现了 24 个断点，包括数据串入、静默丢失、来源错误和入口未传业务标识。

## 1. 范围、证据与判定方法

- 按 PRD 第 1～6 章的模块与契约，核对设计图的页面、卡片、弹窗与按钮。
- 解析生成运行时的函数声明、别名及最终覆盖函数，避免把已被 `businessRules.js` 替代的旧函数误认为实际逻辑。
- 静态解析 423 个函数/别名条目、426 处模板事件绑定和 171 个不同的模板调用函数；本轮解析未发现模板入口函数缺失。
- 浏览器采集 529 个设计模板控件实例、29 个运行页面/弹窗快照、898 个运行控件实例及 1,506 个展示项实例。数量包含重复控件及重复展示，不是独立功能数量，也不是覆盖率。
- 在内存 Vault 与浏览器中执行 24 个有针对性的反例，全部复现；另验证藏金屋收支精度和透支拦截两条正向路径通过。
- 本次重新运行 `npm.cmd run typecheck` 与 `npm.cmd test`，均通过。静态完整性测试主要检查文件、大小、关键字符串和入口函数，不能证明业务闭环。

这不是 Obsidian/Android 真机验收。Obsidian 设置页、命令、原生 Canvas 和外部文件生命周期以源码审查为主。三个旧版“专属统计工作台”经运行检查均被强制切回甘特，因此只按遗留原型评估，不当作用户当前正常可达页面。未宣称对任意输入、所有设备和所有状态排列做了穷尽验证。

审查资料：

- [按钮逐项调用表](BUTTON_TRACEABILITY.md)：设计模板与页面快照中的每个控件、事件入口、函数位置和两层下游调用。
- [展示值逐项快照](DISPLAY_VALUES.md)：每项展示文字及其页面/DOM 位置。
- [运行反例原始证据](browser-evidence.json)：每个反例的输入上下文、实际结果和判定。
- [页面快照 JSON](page-controls.json)、[设计控件 JSON](design-controls.json)、[函数与调用目录](functions.json)。
- `toast-only-candidates.json` 仅为静态候选表；其中可能有真正的 DOM 操作，不能把候选数量直接当作假功能数量。

## 4. 其他已确认的结构缺口

1. **没有形成真正的统一节点事实源与就绪调度器。** `WorkNodeEntity`、`ExecutionCardModel` 接口存在，但运行主要使用HTML、DOM dataset、周任务和档案快照。连线没有驱动 dependencies 校验，计划日期/完成/归档/取消也没有统一决定执行池。新节点一插卡便进入今日，不按所有前置条件就绪。
2. **六类执行页被通用工位替代，缺少卡型专属数据。** 目标实测值、复盘可编辑提升项/派生、自定义实际值、习惯逐项历史、文本阅读次数没有统一回写。`executionRecords[nodeId]`只保留最近一次，历史另在profile中，二者尚无版本和一致性机制。
3. **关联项目图是场馆级静态样例。** `renderExecProjectAssociatedNodes()`读取`EXEC_PROJECT_DATA`，不是当前任务的项目画布。“前置/当前/后续”“查看物证”不能当作真实依赖与证据。
4. **规划端仍保留执行入口。** PRD 2.2与2.4明确不应有进入执行按钮；上一版把它们改成跳转，避免直接盖章，但还没有完成界面职责分离。
5. **更新、删除、归档、重做没有覆盖所有投影。** 重命名规划节点/修改项目分类和期限，不一定更新已插入的待办标题、场馆、周任务和来源标准；归档没有撤销派发；跨日也没有按频次重建一次性/周期任务。
6. **打印、证书、部分画布工具仍为占位。** `printFamilyPact`、证书按钮、部分插图/笔记/表格/物证/相机工具只给提示。必须区分已真正改变DOM的操作与单纯toast，不能按函数名存在判完成。
7. **家庭签署与法典缺少版本源。** 经典解释可作为系统静态资料；但“齐天、齐志远、林婉清、2026-09-01签署、之印”等是HTML样例，不能作为当前家庭的真实签约状态。`personal_code.md`受保护不被覆盖，却没有读取它来渲染查阅页。
8. **事件总线不构成业务事务。** 源码基本没有领域订阅者；包装window函数的成功事件还会在取消/校验失败后发出。`confirmAddProject`与实际`confirmAddNewProject`、`saveDailyNoteEntry`与实际`saveNoteDailyEntry`等名称不一致使钩子静默跳过；内部词法调用也绕过部分window包装。
9. **自定义场馆恢复不完整。** 元数据与项目能够恢复，但建筑位置没有独立持久化；重建布局使用固定位置，筛选胶囊/鹰眼点不是完整对称重建；成就分组还有D22。
10. **原生Canvas只是单向首次导出。** 保留用户原生编辑是正确的数据保护措施，但后续插件修改不会刷新已有Canvas，原生修改也不会回流插件。不能同时声称它与插件脑图共享实时事实源。
11. **日志与附件只做到部分可追溯。** 财务/成就/问道/裁决多数记为自由文本，不含统一eventId/sourceEntityId；执行附件保留在checkinRecords中，尚未统一并入每日随记历史媒体列表。项目、随记、勋章、证据间的反向定位仍有缺口。
12. **随记部分展示值没有真实采集源。** 保存函数没有执行PRD规定的随笔长度与心情/精力确认校验；启发题未按日期轮换；新视频上传没有采集时长元数据，但旧画廊渲染仍使用默认时长文案。文件存在与真实播放已接通，不等于缩略图、拍摄时间、视频时长和字数规则全部完成。

## 7. 建议修复顺序与可验收标准

1. **先解决可能串数据或丢数据的问题**：D03、D04、D17、D20。项目状态与历史栈隔离；模板不可变；跨日先封存草稿。每项加入跨项目/跨日/重开反例。
2. **统一任务事实源和派发**：建立结构化Node、TaskInstance、CheckinRecord及版本；只由依赖、日期、可执行开关和项目生命周期生成日/周/月投影。修D02、D08、D09、D24、D07。
3. **统一验收与聚合口径**：按卡型校验规划要求，保存逐项实测/清单/复盘/自定义值；项目节点进度与每日坚持分开。修D05、D06、D11、D23。
4. **补齐成果、契约、问道与法典引用**：成就/悬赏/裁决/随记引用实体ID和真实附件；动态分组；精准回源；转化/兑现幂等。修D12～D16、D22。
5. **清理原型与边界功能**：真实日期轴、真实打印/证书、可维护家庭档案、清晰的Canvas导入导出关系。修D01、D10、D18、D21及静态缺口。

每项功能至少应能回答：**谁创建数据、唯一实体ID是什么、哪些字段只读、哪些规则必须通过、保存到哪里、哪些投影会更新、重新打开如何恢复、怎样返回原始事实。** 缺少任何一项，都不应仅凭“按钮能点击、页面能打开、出现成功提示”认定闭环完成。
